# 03: Volunteer registers and pays a Trip Fee to confirm a seat

**What to build:** A Volunteer can register on an open Volunteer Batch and pay its Trip Fee. Registering alone does not claim the seat — the seat is held provisionally for a limited window, and only becomes confirmed, and only then counts against quota, once the Trip Fee payment settles. An unpaid hold expires automatically and releases the seat. A full Batch refuses new registrations. This is the core of the whole feature: the first point where real money moves for a Volunteer Trip.

**Scope note (absorbed from Ticket 01 during its planning):** `releaseMaturedEscrow`'s and the settlement webhook's Trip-side generalization both need `Payment.registration.batch.tripId` — a relation chain that only compiles once `Registration` (this ticket) and `VolunteerBatch` (Ticket 02) both exist. Ticket 01 could only generalize the pieces that take their subject as a parameter (the leg-builders, the balance queries) or that filter on a payment/payout's own direct scalar FK (`negativeBalances`, `stuckPayouts` in `/api/admin/reconcile`). This ticket owns the rest: the sweep, the webhook, and reconcile's `strandedEscrow`/`deferredEscrowWatchdog` Trip variants — all listed below, not optional extras.

**Blocked by:** 01, 02

**Status:** ready-for-agent

- [ ] New `RegistrationStatus` enum: `HOLD`, `CONFIRMED`, `EXPIRED`, `CANCELLED`. `HOLD` and `CONFIRMED` together count toward a Batch's `maxQuota`; only `CONFIRMED` counts toward its `minQuota`.
- [ ] New `Registration` model: belongs to one Volunteer (`User`) and one `VolunteerBatch`, a `holdExpiresAt`, a status, and a `payment Payment?` back-relation. This is also where `Payment.registrationId` (added as a plain scalar in Ticket 01) gets its real `@relation` wired up — `Payment.registrationId` should reference this model once it exists, mirroring `Donation.payment`/`Payment.donationId`'s existing shape exactly.
- [ ] `Registration.status` is a denormalized field kept in sync with its `Payment.status` — the same dual-write shape, including a standing guard test asserting no writer sets one without the other, that this codebase already uses for `Campaign.status`/`Campaign.lifecycleStatus`.
- [ ] `POST /api/volunteer-trips/[slug]/batches/[id]/registrations` — the registering Volunteer:
  1. First sweeps this Batch for `HOLD` Registrations whose `holdExpiresAt` has passed and flips them to `EXPIRED` (see the hold-expiry sweep below) — run at the top of the request, no scheduler, the same pattern `releaseMaturedEscrow` already uses at the top of a payout request.
  2. Refuses if `HOLD + CONFIRMED` count on this Batch is already at `maxQuota`.
  3. Creates a `HOLD` Registration and a `PENDING` `Payment` (with `registrationId` set, `donationId` null) for the Trip Fee amount, via the same payment-provider integration `POST /api/donations` already uses, returning the same provider-checkout response shape.
- [ ] The hold-expiry sweep is its own tested function, not inlined only in the route — modeled directly on `releaseMaturedEscrow`'s shape in `lib/money/escrow.ts`. This is a *new* sweep (Registration-hold expiry), distinct from the escrow-maturity sweep in the next item — don't conflate the two.
- [ ] `releaseMaturedEscrow` (`lib/money/escrow.ts`) is generalized so its candidate query and per-payment subject resolution cover Registration-linked Payments, not just Donation-linked ones: where it currently does `donation: { campaignId }` and selects `donation: { select: { campaignId: true } }`, it needs the equivalent `registration: { batch: { tripId } }` / `registration: { select: { batch: { select: { tripId: true } } } }` path, branching on whether the Payment's `donationId` or `registrationId` is set to decide which. The row lock it takes before touching the balance-bearing account (`SELECT ... FOR UPDATE`) locks the `Campaign` row for a Campaign-subject payment and the `VolunteerTrip` row for a Trip-subject one — read that function's existing lock-ordering comment (about the webhook and this sweep never contending on the same Payment row because the webhook only ever writes a Payment while it's `PENDING`) and preserve the same invariant for the Trip path: the webhook's Trip-settlement branch (below) must not write a Payment outside `PENDING` either, or this sweep's deadlock-avoidance reasoning silently stops holding.
- [ ] `POST /api/webhooks/[provider]`'s `paid` branch: when the settling `Payment.registrationId` is set (rather than `donationId`), it takes a structurally different path than the Donation branch — there is no Campaign-equivalent `collectedAmount`/target-met update, because `VolunteerTrip` has no such field in this spec. The Trip branch: include `registration: { include: { batch: true } }` instead of `donation: { include: { campaign: true } }`; on settlement, flip `Registration.status` to `CONFIRMED` (the same status-predicated `updateMany` discipline the Donation branch already uses to survive two concurrent webhook deliveries); post `paymentSettledLegs` with `{ type: 'trip', tripId: registration.batch.tripId }`; and, outside the transaction (same as `notifyDonationConfirmed` today), send a new `notifyRegistrationConfirmed` notification (sibling of `notifyDonationConfirmed`, same "never roll back settled money for a failed notification" reasoning).
- [ ] `POST /api/webhooks/[provider]`'s `failed`/`expired` branch: the Trip-side equivalent flips `Registration.status` to `EXPIRED`, mirroring how the Donation branch flips `donation.paymentStatus` to `'failed'` for both provider outcomes today.
- [ ] `GET /api/admin/reconcile` gains the two Trip-scoped checks Ticket 01 explicitly left out: `strandedEscrow` (a released Registration-linked Payment whose credited net doesn't reconcile against what's actually left `ESCROW_HOLD` on its behalf) and `deferredEscrowWatchdog` (a Registration-linked Payment matured long enough ago that "still deferred by an in-flight refund" stops being the likely explanation), both computed the same way as their existing Campaign versions but resolving the subject via `payment.registration.batch.tripId` instead of `payment.donation.campaignId`.
- [ ] No Platform Fee leg is ever posted against a Trip Fee settlement — assert this explicitly as a regression test, not just an absence.
- [ ] `GET /api/volunteer-trips/[slug]`'s remaining-quota figure (built in Ticket 02) now reflects real `HOLD + CONFIRMED` counts.
- [ ] Two concurrent registration requests against a Batch at exactly one remaining seat: exactly one succeeds, the other is refused with a clear "Batch full" response — not a race that lets both through or a 500.
- [ ] A `HOLD` Registration whose Payment expires (the existing `Payment.expiresAt` mechanism, unchanged) is swept to `EXPIRED` and no longer counts toward `maxQuota` for the next registration attempt.
- [ ] A Volunteer cannot register twice on the same open `HOLD`/`CONFIRMED` Registration for the same Batch (no duplicate concurrent registration from one Volunteer against one Batch).
- [ ] Every existing Campaign-path test in `lib/money/escrow.test.ts`, `api/webhooks/[provider]/route.test.ts`, and `api/admin/reconcile/route.test.ts` still passes unchanged after these functions grow their Trip branch.
