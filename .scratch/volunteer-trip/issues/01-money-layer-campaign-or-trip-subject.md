# 01: Money-layer primitives accept a Campaign or a Volunteer Trip

**What to build:** Nothing user-visible yet — this is the prefactor the rest of the Volunteer Trip spec depends on. Today `Payment`, `LedgerEntry`, and `Payout` only ever belong to a Campaign, and every ledger leg-builder in `lib/money/ledger.ts` hardcodes `campaignId` and `CAMPAIGN_BALANCE`. This ticket generalizes the parts of that machinery that don't require knowing *which* Volunteer Trip a payment belongs to — the leg-builders, `postTransaction`, and the two balance-query functions — without changing anything about how Campaign money behaves today.

**Scope correction (found while planning this ticket, read before starting):** `releaseMaturedEscrow` and the payment-settlement webhook both need to resolve a Trip Fee payment's Trip via `Payment.registration.batch.tripId` — a relation chain through `Registration` and `VolunteerBatch`, neither of which exists yet (`Registration` is Ticket 03, `VolunteerBatch` is Ticket 02). Code that navigates a Prisma relation to a model that doesn't exist in the schema does not compile, so those two generalizations are **not** part of this ticket — they move to Ticket 03, where `Registration`/`VolunteerBatch` both exist by the time it starts (it's blocked by this ticket and Ticket 02). Do not attempt them here; see the reconcile item below for the same reasoning applied to two of its four checks.

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

- [ ] `Payment.donationId` becomes nullable; a new nullable, unique `registrationId` is added alongside it, **as a plain scalar column with no `@relation`** — `Registration` doesn't exist yet, so there's nothing to relate to. Exactly one of `donationId`/`registrationId` is ever set, enforced at the application level (Prisma can't express the constraint). Ticket 03 adds the `@relation` and the `Registration.payment` back-reference once `Registration` exists — leave a comment on the column saying so, so it isn't mistaken for an oversight.
- [ ] `Payout.campaignId` becomes nullable; a new nullable `volunteerTripId` is added alongside it, same exactly-one-of-two shape. If `VolunteerTrip` already exists in this branch's history when you implement this (check `prisma/schema.prisma` first — Ticket 02 has no dependency on this ticket and may have landed first), wire up the real `@relation` and `VolunteerTrip`'s back-reference now; if not, add it as a plain scalar with the same "relation added later" comment as above, and note in your report which case applied.
- [ ] `LedgerEntry` gets a new nullable `volunteerTripId` alongside its existing nullable `campaignId`, with the same existence check and either-relation-or-plain-scalar-for-now treatment as `Payout.volunteerTripId` above. A Trip-scoped entry sets `volunteerTripId` and leaves `campaignId` null; a Campaign-scoped entry does the reverse; a platform-level entry leaves both null, unchanged from today.
- [ ] `LedgerAccount` gains one new value, `TRIP_BALANCE` — the Trip-scoped sibling of `CAMPAIGN_BALANCE`. No other new account is added: `ESCROW_HOLD`, `GATEWAY_CLEARING`, `PROVIDER_FEE`, `PAYOUT_CLEARING`, and `REFUND_CLEARING` are reused exactly as they are today for Trip Fee money, distinguished only by which FK (`campaignId` vs `volunteerTripId`) the entry carries.
- [ ] `paymentSettledLegs`, `escrowReleaseLegs`, `refundLegs`, and `payoutInstructedLegs` (`lib/money/ledger.ts`) each take a `subject: { type: 'campaign'; campaignId: string } | { type: 'trip'; tripId: string }` in place of their current bare `campaignId` parameter, picking `CAMPAIGN_BALANCE`/`TRIP_BALANCE` and the matching `LedgerEntry` FK accordingly. `refundLegs`'s `source` parameter grows a `'TRIP_BALANCE'` option alongside its existing `'ESCROW_HOLD' | 'CAMPAIGN_BALANCE'`. These four functions take their subject as a parameter from the caller — they never look anything up themselves — so they're fully buildable and testable now with a synthetic trip id string, no `VolunteerTrip` row required.
- [ ] `campaignBalance`/`escrowBalance` (`lib/money/ledger.ts`) gain a way to query the Trip-scoped equivalents — either new sibling functions (`tripBalance`/`tripEscrowBalance`) or the existing two functions grow the same subject parameter. Pick one; don't leave two divergent implementations of the underlying account-balance query. These only read `LedgerEntry.volunteerTripId` directly, so they're also fully buildable now.
- [ ] `postTransaction` itself needs no change — verify this explicitly with a test, since it already just posts whatever legs it's given and asserts they balance.
- [ ] `GET /api/admin/reconcile` gains **only** the two of its checks that don't need to traverse through `Registration`/`VolunteerBatch`: a Trip-scoped `negativeBalances` (group `LedgerEntry` by `volunteerTripId`/`account`/`direction`, check `['ESCROW_HOLD', 'TRIP_BALANCE']`, same shape as the existing Campaign check) and a Trip-scoped `stuckPayouts` (the same `processing`/`approvedWithoutProviderRef` queries, filtered on `volunteerTripId: { not: null }` instead of implicitly-Campaign). Do **not** attempt `strandedEscrow` or `deferredEscrowWatchdog`'s Trip variants here — both need `payment.donation.campaignId`'s equivalent (`payment.registration.batch.tripId`), which doesn't compile without `Registration`/`VolunteerBatch`; those two land in Ticket 03 alongside the webhook and sweep generalization.
- [ ] Every existing Campaign-path test in `lib/money/ledger.test.ts`, `lib/money/escrow.test.ts`, `lib/money/payouts.ts`'s tests, `api/webhooks/[provider]/route.test.ts`, and `api/admin/reconcile/route.test.ts` still passes unchanged.
- [ ] New tests exercise the Trip-subject path directly through the leg-builder, balance-query, and (the two in-scope) reconcile seams using a synthetic trip id — no `VolunteerTrip` model is needed for this ticket's own tests to be real, since none of this ticket's scope reads through a relation to one.
- [ ] Regression test: a `TRIP_BALANCE` entry can never be summed into `campaignBalance`'s result, and a `CAMPAIGN_BALANCE` entry can never be summed into the Trip-scoped balance query, however either is queried.
