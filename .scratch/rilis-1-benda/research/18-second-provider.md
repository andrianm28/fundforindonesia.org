Research for `.scratch/rilis-1-benda/issues/18-second-payment-provider.md`.
Candidates per the ticket: Xendit, Midtrans, DOKU, Flip for Business.

**Access date for all citations below: 2026-09-28.**

**Method note.** This session's outbound network proxy blocks direct fetches
(`WebFetch`) to `xendit.co`, `docs.xendit.co`, `help.xendit.co`,
`midtrans.com`, `docs.midtrans.com`, `docs.doku.com`, `developers.doku.com`,

server-side and returns the source URL; I did not render or double-check the
live page myself. Each row cites the specific primary-source URL the search

under **Unknowns**, not guessed. Before committing to a choice, the builder
implementing the adapter should load the actual page (their session's egress
may not be restricted the same way) and confirm the numbers, especially fees
and settlement timing, which vendors revise.

## Fit with this repo's Payment model and ADRs

- **Provider-neutral interface (ADR 0006).** All four candidates fit the shape ADR 0006 already assumes: one `PaymentProvider` adapter per vendor, one webhook route + signature check per vendor, Payment records which provider issued it. None of this needs re-litigating regardless of which candidate wins.

- **Provider Fee must come from the payload, not be computed (CONTEXT.md `Provider Fee`, ADR 0006 consequence).** Sumopod's webhook hands the adapter `fee` and `net_amount` directly. For the candidates:
  - Midtrans's classic notification signs only `order_id + status_code + gross_amount`, and its documented payload does not appear (from what was reachable) to include a `fee` field the way Sumopod's does — historically Midtrans doesn't return provider fee in the transaction/notification payload at all, since Midtrans fees are billed to the merchant separately rather than netted per transaction. **This needs primary confirmation** before assuming an adapter can populate `Payment.providerFee` the same way the Sumopod adapter does; if Midtrans doesn't expose it per-transaction, the adapter would have to compute it from the published rate card, reintroducing the "adapter computes its own fee" pattern ADR 0006 explicitly flagged as wrong for Sumopod's zero-fee bug.
  - Xendit's Invoice/Payment Request objects are commonly understood to include a `fees` breakdown, but no primary text with the exact field name was reachable this session to cite — **unconfirmed, flagged below**.
  - DOKU's SNAP payment notification schemas were not reachable in enough depth to confirm a `fee` field either.
  - **None of the four could be confirmed, from primary sources reachable this session, to carry both a real-time fee and a settlement-date estimate on the same webhook the way Sumopod's `fee`/`net_amount`/`settled_at` triad does.** This is the single most consequential unknown for adapter design and Escrow Hold accuracy (see `docs/integrasi-sumopod.md` §"Waktu dan Escrow") — if the second provider's webhook doesn't carry a settlement estimate, the same `paid_at + T+N` fallback pattern Sumopod's adapter uses will likely have to be reused, with N sourced from the provider's docs rather than the payload.

- **Webhook signing schemes differ meaningfully from Sumopod's svix HMAC, and from each other:**
  - **Xendit**'s `X-CALLBACK-TOKEN` is a static shared secret compared directly — not an HMAC over the body, and not tied to a timestamp or nonce. This is a materially weaker scheme than Sumopod's svix (no anti-replay, no coverage of the payload's integrity beyond "the token was known") and would need its own threat-model note if chosen; `docs/integrasi-sumopod.md`'s anti-replay-window pattern doesn't carry over.
  - **Midtrans**'s classic `signature_key` covers only three named fields (`order_id`, `status_code`, `gross_amount`), explicitly not the full body — this is the exact "Midtrans-shaped celah" (gap) already called out in `docs/integrasi-sumopod.md`'s closing note: `transaction_status` and any `fee` field sit outside the signed content and could in principle be replayed with a different status. The adapter would need the same defensive re-check pattern the existing Midtrans-style code already carries (per ADR 0006 "kept as adapters, not thrown away").
  - **DOKU**'s SNAP symmetric signature (`HMAC_SHA512` over method + endpoint + access-token + body-hash + timestamp) is the strongest of the four on paper — it does cover the full body (via a hash) and binds the request to method/endpoint/timestamp — but requires implementing the SNAP access-token flow (OAuth-like symmetric/asymmetric client credentials) as a prerequisite, which is more integration surface than Sumopod's static webhook secret.
  - **Flip**'s callback verification could not be confirmed in enough technical depth from primary sources reachable this session — this is a real gap in the evidence, not a "Flip is fine" finding.

- **Disbursement (the ticket's core ask).** All four expose a disbursement/payout API, unlike Sumopod (ADR 0006: "no disbursement API... payouts done by hand"). Adding any of them would be the first provider in this codebase where `createPayout` isn't rejected with `SumopodNotSupportedError` (`docs/integrasi-sumopod.md`) — i.e. the first real exercise of the two-person manual-payout path being optionally replaced by an API call. That's a design decision for the ticket that picks the provider, not this research: does Rilis 1 keep the manual two-person Payout flow (ADR 0006's controls) even once an API exists, or does it start wiring the API? ADR 0006 says the two-person rule and mandatory proof "are not optional... and neither is dropped when a provider with a disbursement API is added later" — so at minimum, any auto-disbursement capability must not remove that control, only potentially automate the transfer leg while approval and proof stay as-is.

- **Merchant account separation (ADR 0011) and Collecting Entity vs. Platform Operator (ADR 0009, CONTEXT.md).** Whichever provider is chosen needs its own merchant account, separate from Sumopod's and separate from Makam.co.id's, per ADR 0011 — none of the four candidates change that requirement. The KYB question in the ticket ("for PT Jaya Korpora Prima as Platform Operator with YIEM as Collecting Entity") maps onto a real tension already named in ADR 0009: the merchant account is held by the Operator (a PT, a limited company), but Indonesian rules on public-donation collection most likely require the *permit holder* to be a foundation, so the Collecting Entity's name (YIEM) needs to appear on the compliance side of onboarding even though the Operator's entity opens the merchant account. Only Xendit's help-center text explicitly and directly addresses onboarding a Foundation/NPO merchant profile; the general "Indonesia" KYB pages found for Midtrans, DOKU and Flip describe PT/CV/PMA-style business registration without addressing the two-entity (Operator holds account, partner org holds the permit) structure this platform actually needs. **ADR 0009 says "Counsel must confirm the arrangement before launch"** — that holds regardless of which provider is picked, and this research cannot substitute for that legal confirmation.

## Unknowns (could not confirm from primary sources reachable this session)

1. **Whether any candidate's payment-webhook payload carries both a provider fee and a settlement-date estimate**, the way Sumopod's `fee`/`net_amount`/`settled_at` triad does. This is the single most important open question for Escrow Hold correctness and should be the first thing verified — by reading the actual API reference (Xendit Invoice/Payment Request webhook schema, Midtrans `HTTP(S) Notification` full payload schema, DOKU SNAP Payment Notification schema, Flip's Accept-Payment callback schema) — before an adapter is built.
2. **Exact e-wallet and virtual-account per-transaction fees for Xendit and Flip.** Search results returned pricing language ("fixed processing fee plus a payment method fee", "only pay for successful transactions") but not the Rupiah/percentage rate card; Xendit and Flip likely gate exact rates behind a sales conversation or a logged-in dashboard.
3. **Midtrans and Flip disbursement (Payouts/Iris, Big) fees.** Not found in text reachable this session; commonly negotiated per merchant rather than published, but that is inference, not a confirmed primary-source fact.
4. **Full settlement-timing tables for DOKU and Flip** (T+N by method) — not found in the primary text reachable this session.
5. **Flip's webhook signature mechanism in technical detail** — whether it is HMAC-based, what it covers (full body vs. named fields), and any anti-replay measure.
6. **Full KYB document checklists for Midtrans, DOKU, and Flip when the merchant is a foundation/NPO acting as Collecting Entity**, and specifically whether any of them supports the two-entity structure (Operator's PT holds the merchant account; a different partner foundation's fundraising permit is what's actually being relied on) the way ADR 0009 describes. Only Xendit's foundation-support article was reachable and confirmed.
7. **Production base URLs, rate limits, and per-transaction nominal caps** for all four — none of this was covered in the searches run, and `docs/integrasi-sumopod.md` shows these details (e.g. Sumopod's undocumented production base URL, no read API for balance) mattered a great deal in practice.

Given how much sits in "Unknown," this file should be treated as a **shortlist narrower than a decision**: it rules out no candidate on hard technical grounds, and it surfaces exactly which primary-source pages someone with working access to these vendor domains needs to open next.

## Recommendation (Sonnet's opinion — the choice is the owner's)

**Recommend: Xendit**, with DOKU as a close runner-up worth a second look if the webhook-fee/settlement question below resolves in DOKU's favor.

Reasons:

- Xendit is the only candidate with a **primary-source-confirmed path for onboarding a Foundation/NPO merchant profile**, which is directly relevant to how this platform's Operator/Collecting-Entity split (ADR 0009) will need to be represented in the provider's KYB — even though final confirmation still needs counsel, per that ADR.
- Xendit's VA/e-wallet coverage (6 VA banks, 7 e-wallets including GoPay/OVO/DANA/LinkAja/ShopeePay) is the most extensively documented in primary sources among the four, closing the QRIS-only gap Sumopod leaves (`docs/integrasi-sumopod.md` §"Sudah dikonfirmasi ke Sumopod": "Donor yang tidak bisa memindai QRIS tidak punya cara membayar").
- Xendit's Disbursement API is confirmed with a specific, citable fee (Rp2,500 excl. PPN) and an ETA field in the response — useful for finally offering an alternative to the fully-manual two-person Sumopod payout path, while still keeping the two-person approval control (ADR 0006).
- Xendit has a confirmed, auto-provisioned sandbox with a known test balance, which matters for integration-test-driven development per this repo's TDD workflow.

Caveats that should give the owner pause before this becomes final:

- Xendit's webhook signing (`X-CALLBACK-TOKEN`) is a **static shared-secret comparison, not an HMAC over the body** — weaker than Sumopod's svix scheme and weaker than DOKU's SNAP symmetric HMAC. If webhook integrity is a priority equal to payment-method coverage, DOKU's signature scheme is the stronger primary-sourced option, at the cost of implementing the SNAP access-token flow.
- Whether Xendit's payment webhook actually carries a fee and settlement estimate on the same event (the property this ticket explicitly asked to check against Sumopod's pattern) is **unconfirmed** — this recommendation would weaken considerably if that turns out to be false and the fee has to be looked up separately or computed.
- DOKU's e-wallet fee schedule (search-quoted from DOKU's own pricing page) looks meaningfully cheaper for OVO/ShopeePay/LinkAja *if* those quoted percentages hold up under direct verification — worth re-checking before ruling DOKU out purely on the weaker foundation-onboarding evidence trail.

Runner-up: **DOKU**, for the stronger webhook signature scheme and a fee schedule that (unverified) looks competitive, but weaker primary-sourced evidence on foundation/NPO onboarding specifically.

Not recommended for the *second* provider slot right now: **Midtrans** (weakest webhook signature scheme of the four — the exact class of gap `docs/integrasi-sumopod.md` already calls out as Midtrans-shaped — though the codebase already carries a Midtrans-style adapter stub per ADR 0006, which is a real integration-cost argument in Midtrans's favor that this research does not attempt to weigh against the security caveat); **Flip for Business** (too much of its technical surface — webhook signing, VA bank list, fee schedule, KYB checklist — could not be confirmed from primary sources reachable this session to recommend it with any confidence).
